# Cofer: Audit (full, v2)

## Verdict

**Grade: 8.2 / 10** (weighted 8.23, rounded down). No cap binds. The 8.9 cap for an open Medium is above the score.

Cofer's contracts are small, non-upgradeable and carefully built:
- exits are never gated
- every non-unanimous vote waits the exit window
- prices fail closed
- the contracts pass 96 tests, a 100,000-call invariant run and mainnet fork tests

The grade is down 0.3 from the last rescore because of one new off-chain finding. **M-1** (present since the first commit and missed by both earlier runs): `/send @handle` looks up the payee with SQL `ILIKE`, so the `_` in a Telegram username is a wildcard. The bot can pick a different user's key and label it with the name the proposer typed. That is the single most important fix, and it's a one-line change.

## Findings

### M-1. Medium: `/send @handle` can resolve to a look-alike user's key (`_` is a wildcard)
- id: `offchain-backend|services/src/bot/bot.ts|handle-ilike-wildcard`
- location: `services/src/bot/bot.ts:227-237` (`resolveMember`), used by `/send` (`bot.ts:443`) and `/allowance` (`bot.ts:454`)
- path:
  1. A member sends `/send 50 @bob_smith` (`parseSend`, `bot/parse.ts:81`).
  2. `resolveMember` runs `users.findFirst({ where: ilike(username, "bob_smith") })` (`bot.ts:230`). In ILIKE, `_` matches any one character, so `bobxsmith`, `bob1smith` and so on also match. `findFirst` has no ORDER BY.
  3. The first matching row with a key is taken, and its address is cached under the typed name: `nameCache.set(addr, "@bob_smith")` (`bot.ts:235`).
  4. The proposal summary that everyone sees ("Send 50 USDG to @bob_smith", `core/proposal.ts` `describe`) shows that label. Only the signer page shows the real address (`signCheck.pageSummary`).
  5. If members approve, `TRANSFER` pays the look-alike's address.
- trigger: anyone can register a Telegram username one character away from a group member's underscore name, and link a key with the bot (open to all). It then needs an honest member to `/send` to that handle, and voters who trust the label over the address. `/allowance @bob_smith …` resolves through the same lookup: it works only if the look-alike is already a member (`SET_ALLOWANCE` requires an active member, `CoferPot.sol:419`), and then gives them a recurring no-vote allowance (`CoferPot.sol:152-164`).
- impact: one proposal's transfer amount goes to the wrong person. It is bounded by the vote, the guard delay and the members' own review of the address. Funds already in a pot are not otherwise reachable.
- severity: loss of funds × unlikely (needs a prepared look-alike and voters who don't check the address) = **Medium**.
- evidence: **PoC** `PoCs/services/handleWildcard.poc.test.ts` (copy it into `services/test/` of a repo copy to run; see the PoCs README), run against a throwaway local Postgres with the repo's own migrations. 3/3 pass:
  - (a) the intended user has no key: the attacker's `bobxsmith` is returned
  - (b) both users exist: two rows match, and `findFirst` returned the attacker
  - control: an exact `lower(username) = 'bob_smith'` match returns only the intended user, or nothing
- fix (all three are needed):
  1. Exact match: `eq(sql\`lower(${users.username})\`, handle.toLowerCase())`, after checking the handle against Telegram's username pattern `^[A-Za-z0-9_]{5,32}$`. That also rejects `%`.
  2. Only resolve users who are active members of this pot, and refuse if more than one row matches. `users.username` is not unique (`db/schema.ts:54`) and is refreshed only on `/start` (`bot.ts:263-266`), so a stale name can be taken over by someone else even with an exact match.
  3. Label the address with the **stored** username, not the typed one.
- regression test: two users `bob_smith` and `bobxsmith`; resolving `@bob_smith` returns only `bob_smith`. With `bob_smith` missing, it returns nothing.

### Lows

| # | Finding | Location | Path / impact | Fix |
|---|---|---|---|---|
| L-1 | A re-signed vote counts in the services after an on-chain revoke | `services/src/services/proposals.ts:165-171` | `addSignature` upserts with `revoked: false`. A revoke made *before* the first signature updates no row at all (`indexer.ts:198-202`), with the same result. If a member revoked on-chain (`CoferPot.revokeVote`; there's no product path, so it's a direct contract call) and then signs the same proposal again, the database counts the vote, but the contract skips it forever (`CoferPot.sol:387`). The tally shows "ready", the relayer simulation fails with `NotEnoughVotes`, and the retries and the `vote-stuck` alert run until the deadline. Wrong accounting, no loss. | In `addSignature`, read `pot.revoked(digest, signer)` and refuse with "you withdrew this vote on-chain; propose again". |
| L-2 | `/newpot` is not limited to group admins | `services/src/bot/bot.ts` (`newpot` handler); unique `pots_chat_idx` | Any member with a key can open the group's single pot first and become its only founding member, so admission votes start with them. The bot's own text says "An admin can run /newpot" (`bot.ts:155`). Griefing: the group has to start over in a new chat. No funds are at risk, since members only deposit after joining. | Check `ctx.getChatMember(from.id)` is `creator` or `administrator` before creating. |

**Leads (no deduction):**
- **I-3:** `SafeTransferLib.balanceOf` returns 0 when `balanceOf` reverts. An exit then skips that asset, and `_prune` could drop it from `_held`. This only matters if a Stock Token's `balanceOf` can revert (pause normally blocks transfers only). Settle it with the issuer's token source, or a fork test that pauses a real Stock Token.
- **No L2 sequencer-uptime check** in `CoferFactory._price18`. Staleness limits bound the impact and exits never read prices. Settle it by checking whether Chainlink publishes a sequencer feed for chain 4663.
- **Telegram group upgrade** (group → supergroup) changes the chat id, so the pot is no longer reachable from that group. The new private-chat `/exit` keeps exits open.
- **Signer API has no rate limit** on its session-only, RPC-backed reads (`pot.get`, `previewExit`). Sessions come only from bot links.

- **Counterfactual-account signatures:** the services accept ERC-6492 signatures (`proposals.ts:162`, `router.ts:134`), but the contract does not, and an invalid signature reverts the whole `execute` (`CoferPot.sol:388-390`). A member who links a never-deployed account by calling the API directly could block a proposal until its deadline. Onboarding deploys the account first (`web/client.ts:244`). Settle it by refusing 6492-only signatures in `addSignature`.
- **A queued vote can stick:** once a vote is `queued`, `addSignature` refuses new signatures (`proposals.ts:147`), so a vote that loses a signer to an on-chain revoke can't gain a replacement and waits until its deadline. Liveness only.

**Info:**
- `zod` 3.25.76 High advisory (GHSA-mrhx-c7xc-m3w5): **not reachable**. No zod collection schema (array, set, record, map or tuple) exists in `services/src`. Upgrade anyway.
- `esbuild` moderate: dev tooling only.
- I-4: tokens sent straight to a pot are not distributed.
- I-8: `FeeRouter` ownership changes emit no events. This is scored under D.
- `relayer.ts:6` says members can `revokeVote` through userOps; no product path does.
- CI's `foundry-toolchain` step has no `version:`, so the Forge version in CI floats (solc, optimizer and EVM settings are pinned in `foundry.toml`).

**Accepted / documented (SECURITY.md):**

- after-hours price moves within the 12h deposit limit (M-1 remainder from the first audit)
- the daily USDG window: 24h limit vs feed updates every 24h plus up to about 30 seconds (accepted Low)
- exits are in kind
- the guardian wallet is also a Safe owner and receives all fees
