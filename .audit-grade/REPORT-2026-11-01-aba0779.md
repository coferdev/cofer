# Cofer: Audit

**Repo:** github.com/coferdev/cofer · **Commit:** `aba0779` (2026-10-31) · **Mode:** full · **Rubric:** v2 · **Date:** 2026-11-01
Everything ran: forge 1.8.7 (build, 70 tests, coverage), bun 1.4.4 (typecheck, 310 tests, coverage, `bun audit`), plus 7 proof tests. All runs used a scratch copy of the commit with install scripts off.
The card provider is closed and out of band. Only the in-repo stub was audited.

## Verdict

**Grade: 4.0 / 10.** Weighted score 4.06. The binding limit is the score itself, which sits below the 5.0 cap for two open Highs. The 8.0 cap (no invariant tests) and the 8.9 cap (open Medium) also apply. The independent check came to 4.1, which is within the 0.3 band (see the end).

Cofer is a small, carefully written group account: one EIP-1167 clone per group, in-kind exits that can never be gated, and votes as EIP-712 signatures. The exit path is solid and well tested. What holds the grade back:
- Swaps skip the exit window, so a colluding majority can drain the minority in one transaction (H-2).
- The card feature, as shipped, sends members' money to a burn address on mainnet (H-1).
- There are no invariant tests, CI is unhardened, and there is almost no security documentation.

**Most important fix:** H-1. It's one hour of work and it stops a guaranteed loss at launch.

## Findings

### H-1. High: `/card` on mainnet pays the member's allowance to `0x…dEaD` and reports a card as issued
- id: offchain-backend|services/src/index.ts|stub-adapter-in-production
- location: `services/src/index.ts:21-26` (`cards()`), `services/src/cards/StubCardAdapter.ts:13`, `services/src/env.ts:44`, `services/src/web/client.ts:303-311`, `services/src/bot/bot.ts:407-415`
- path:
  1. `CARD_ADAPTER` defaults to `"stub"` (`env.ts:44`), and `CHAIN_ID` defaults to 4663 (`env.ts:15`).
  2. `cards()` throws for `"provider"`, so `StubCardAdapter` is the only adapter that can run (`index.ts:22-25`).
  3. Any linked member runs `/card`, which is listed in `/help` (`bot.ts:407`, `bot.ts:453`).
  4. The signer page calls `card.quote` and gets `fundingAddress = 0x…dEaD` (`StubCardAdapter.ts:13,25`).
  5. The page sends `CoferPot.spend(0x…dEaD, amount × 1.015, memo)` from the member's smart account (`client.ts:308-309`).
  6. `card.confirm` returns `status: "issued", last4: "0000"` (`StubCardAdapter.ts:38-41`), and the member sees "Card order issued".
- trigger: any member with an allowance, in the normal flow. No special state is needed.
- impact: USDG leaves the shared pot permanently. The loss is bounded by the member's allowance per period, and it repeats every period. Every group is exposed once mainnet runs these services.
- evidence: `PoCs/services/cardStub.poc.test.ts`, 2/2 pass on `aba0779`.
- fix (smallest first):
  1. In `cards()`, refuse the stub unless `CHAIN_ID === 46630`.
  2. Hide `/card` from the bot and `/help` when no provider is configured.
  3. Make the stub's funding address a required argument with no burn-address default.
- regression test: start-up with `CHAIN_ID=4663` and no provider throws, and `/card` replies "not available".

### H-2. High: a majority can drain the minority through back-to-back swaps in one transaction
- id: evm|contracts/src/CoferPot.sol|swap-skips-guard-delay
- location: `contracts/src/CoferPot.sol:208` (delay is 0 for `SWAP`), `CoferPot.sol:434-467` (`_swap`), `contracts/src/SwapAdapter.sol:46-54` (only the path's endpoints are checked)
- path:
  1. Members of the passing majority (e.g. 3 of 5) create Uniswap v3 pools for a token they control (e.g. USDG/X and X/TSLA). They pre-sign N `SWAP` proposals with distinct random nonces, each routed through those pools with `minOut` at the oracle floor (`CoferPot.sol:447-449`; the floor is `maxSlipBps` under the oracle, 3% by default).
  2. `execute` sets `delay = 0` for every `SWAP` (`CoferPot.sol:208`). Nothing limits swaps per block or in total.
  3. The adapter accepts any intermediate hop (`SwapAdapter.sol:52-53`). Each swap pays the pot only the floor, and the pools keep the rest.
  4. `execute` is permissionless, so a helper contract submits all N swaps in **one transaction**. The minority can't exit in between.
- trigger: a colluding majority of members. This is exactly the adversary that `guardDelay` exists to stop. The README limits its swap carve-out with "the assets stay in the pot, and an oracle floor bounds the price". That holds for one swap, not for N in a row.
- impact: per swap, the pot loses up to `maxSlipBps` plus the 0.30% fee. Twenty swaps at the default 3% cost the minority **48.7%** of its value in one block. With `maxSlipBps` at its 10% maximum, the loss is near total.
- evidence: `PoCs/contracts/AuditPocs.t.sol::test_poc1_majoritySwapLoopDrainsMinorityInOneTx` passes. The minority's value goes from 2,000.00 to 1,026.27 USDG, and the route owner gains 2,211.73 USDG. The control `test_poc1_control_transferIsQueuedAndMinorityExitsFirst` passes: the same value moved by `TRANSFER` is queued, and the minority exits in full. The PoC models the colluders' pools as the mock router paying 2.99% under the oracle. Sandwiching a real pool, or routing through pools they own, gets the same result, because the contract checks only the oracle floor.
- fix: apply `guardDelay` to non-unanimous `SWAP` too, the same as every other kind. If swaps have to stay instant, then:
  - allow at most one swap per pot per `guardDelay` window, or set a cumulative slippage budget per window;
  - require every hop token in the route to be listed in the factory.

  This is a change to `contracts/src`, so it needs the owner's explicit approval and a re-audit.
- regression test: the PoC above must revert from the second swap onward, or queue.

### M-1. Medium: deposits are priced on stock feeds up to 4 days old, so a member can deposit and exit at a profit
- id: evm|contracts/src/CoferPot.sol|stale-nav-deposit-arbitrage
- location: `CoferPot.sol:295-325` (`navUsdg`, `_deposit`), `CoferFactory.sol:20,111` (`MAX_STALENESS_CAP = 4 days`), `services/scripts/build-asset-list.ts:24` (the mainnet listing script uses the full 4 days), `services/src/bot/bot.ts:32` (default `entrySpreadBps = 50`)
- path:
  1. The pot holds a Stock Token. Its feed last updated at Friday's close, which is still "fresh" for up to 4 days (`CoferFactory.sol:111`).
  2. The token's market price moves (weekend news). The feed doesn't.
  3. A member deposits USDG. The shares are priced at the stale NAV, minus only the 0.5% spread (`CoferPot.sol:313-319`).
  4. The member exits at once, in kind (`CoferPot.sol:327-351`), and receives tokens worth the market price.
- trigger: any member, whenever the price moves more than `entrySpreadBps`. This is a timing condition.
- impact: value moves from the other members to the depositor. With a +10% move, a 4,000 USDG round trip nets **+139 USDG**, and each honest member loses about 35 USDG. The beta deposit cap holds this down only in the bot and signer page (`core/betaCap.ts`). The contract has no cap.
- evidence: `test_poc2_staleFeedDepositThenExitDilutesOthers` passes (paid 4,000.00, got 4,139.33 at market). The control `test_poc2_control_freshFeedNoProfit` passes.
- fix: give deposits a much tighter staleness limit than swaps. For example, close deposits while any held non-USDG feed is older than about 1 hour (markets closed means deposits closed). Alternatively, scale the entry spread with feed age. This changes `contracts/src`, so it needs approval and a re-audit.
- regression test: the PoC-2 deposit reverts with `StalePrice` after a 3-day warp.

### M-2. Medium: the signer site controls what every passkey signs, contrary to "the studio cannot move funds"
- id: offchain-backend|services/src/web/client.ts|server-controls-what-is-signed
- location: `services/src/api/server.ts:64` (serves `/assets/signer.js`), `services/src/web/client.ts:186-194` (signs server-supplied `typedData` without decoding it), `client.ts:236-241` (builds `exit(shares, to)` itself), `README.md` rule 3
- path:
  1. Member keys are Kernel accounts whose sudo validator is a passkey. The WebAuthn prompt shows no transaction details.
  2. The signing JavaScript comes from the same server that supplies the typed data. A changed bundle, or a changed `proposals` row, can show "Send 5 USDG to Alice" and have the passkey sign anything. For example, `exit(allShares, attacker)` runs with no vote and no delay.
- trigger: a malicious operator, or a compromise of the API host, its build, or a dependency in the bundle (`@zerodev/*` are caret-pinned). This is an unlikely trigger.
- impact: every member who opens a link during the compromise can lose their whole share.
- evidence: traced by reading. This is an architectural property, so there's no PoC.
- fix:
  1. Correct README rule 3, and record this in SECURITY.md as an accepted risk with the reason (this drops the deduction to −0.4).
  2. Then harden: decode the typed data in the page and compare it with the summary; serve the bundle with SRI from an immutable, versioned location; pin `@zerodev/*` exactly.

### M-3. Medium: a vote made outside the bot is queued and executed with no group notice
Found by the independent check. Confirmed by reading.
- id: offchain-backend|services/src/indexer/indexer.ts|unknown-digest-silent
- location: `services/src/indexer/indexer.ts:128-135`, `services/src/notifier/notifier.ts:117-118`
- path:
  1. Colluding majority members sign a `TRANSFER` with their own keys, without going through the bot. EOA members are supported (`router.ts:126`).
  2. Anyone calls `execute`, which emits `ProposalQueued` (`CoferPot.sol:211-214`).
  3. The indexer updates the `proposals` row by digest. There's no row, so nothing changes (`indexer.ts:128-130`).
  4. The notifier's `load()` returns null for an unknown id, so no group message is posted (`notifier.ts:117-118`). `ProposalExecuted` is silent in the same way.
  5. After `guardDelay` (6h by default) the transfer runs.
- trigger: a colluding majority, the adversary `guardDelay` exists for.
- impact: the exit window still exists on-chain, but members who rely on the bot never hear about it. They can lose up to their whole share. It's rated Medium rather than High because anyone watching the chain still gets the full window.
- evidence: traced by reading. No PoC was run (it needs the DB and queue mocked).
- confirming test: feed `handlePotLog` a `ProposalQueued` log with an unknown digest, and assert a chat message is queued for the pot's group. On `aba0779` none is.
- fix: on `ProposalQueued` or `ProposalExecuted` for an unknown digest, post a group alert ("A vote not made through the bot was queued: kind X, runs at T. You can /exit before then.") and alert the ops chat.
